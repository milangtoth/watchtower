# Bring Watchtower up to the Patterno challenge brief

You are working with me and three teammates in the Watchtower repository. Take the existing Rust service from its present state to a submission we can defend against Patterno's independent tests. Patterno will start our container, give it the address of a previously unseen procurement portal, and pull data and files through our API. Our job is to attach autonomously, deliver every open tender and its documents, notice incorrect delivery even when the site still returns HTTP 200, and recover when possible. A human must be able to tell what happened the next morning.

Read all three pages of [the original brief](../Patterno-Track-Description.pdf) and [AGENTS.md](../AGENTS.md) first. Page 1 defines judging and operating rules, page 2 describes test coverage and hand-in, and page 3 defines the exact HTTP and data contract. Give the PDF precedence on challenge requirements. Work from the current checkout, including teammates' uncommitted work.

## Work through these risks in order once approved

### 1. Make `serving` trustworthy

Start with a reproducible false-success case. In [the reader](../src/recipe.rs), inspect `read` and `parse_listing`. A missing next link can end the loop, a configured total that fails to parse can disappear, and the reader sets `terminal_page` to true at successful loop exit. The [worker](../src/worker.rs) checks several losses on previously open records, but equal counts and nonempty fields can conceal a bad read. [Publication](../src/db.rs) closes previously open records that are missing from a candidate accepted as complete. These paths can combine to publish partial data and false closures. The local HTTP smoke checker tests one file and expects a nonempty serving portal.

Build a small independently enumerated fixture and reproduce the risk before changing policy. Include a page-two-only tender, an HTTP-200 change to pagination, a missing or malformed total, a genuine empty result, a plausible value taken from the wrong column, and a document attached to the wrong tender with total file count unchanged. Include controls where a tender really disappears or a buyer legitimately replaces a document. Show which checks can distinguish these cases, what evidence an ambiguous case lacks, and when to escalate to Luna. Bring me the publication and closure rule for approval before implementing it. On the accepted design, demonstrate that an incomplete read cannot overwrite the verified snapshot or falsely close tenders and an unchanged, healthy read still needs zero calls.

### 2. Demonstrate unfamiliar-portal attachment

Use the exact human-facing portal address as the sole input. Start with isolated, empty state. Label a fresh run on a known development portal as a cold start. Reserve the blind-test label for portals or fixture variants withheld from implementation and tuning. Compare against independently collected results only after the run. Record the submitted URL, run IDs, state/reason, elapsed time, pages, expected and delivered tender identities, file matches by tender, misses, extras, and caps encountered. A direct-JSON trial can localize a failure between discovery and extraction. Record it separately from the public-page trial. Use manageable listings with a defensible total and date-stamped scope when making a full-coverage claim.

- **DTVP.** Reproduce why discovery sees featured entries and an empty search template. Identify the actual public listing and end-of-list evidence. Check the document path from notice to project workspace to attachments. Keep failure explicit if complete enumeration cannot be established.
- **Ireland.** Trace the public listing through the document index and anonymous download confirmation. Distinguish a public, read-only interaction from account or bid actions. The baseline contains ZIPs. Compare published member names, lengths and hashes against independently unpacked members.
- **Catalonia and TenderNed.** Test what can be discovered from the public page, then whether the runner can follow numbered JSON pages, use source identifiers to reach detail and attachment data, and assign the correct file to each tender. The current recipe handles explicit links and JSON pointers. Present any proposed bounded recipe operations, browser capability or new dependency as a decision. Explain how old saved recipes would continue to work and how every request would obey the rate limit. Avoid portal-specific code or hand-authored runtime hints as a substitute for learning.

Use the UK collection as a regression. Preserve the mix of server-rendered pages, JS-backed listings, multi-step downloads and access gates. Recheck source availability and deadlines at run time. Five spot-checked documents establish a benchmark. Demonstrating every open tender and each in-scope document requires a complete source inventory for the claimed scope, including detection of extras.

### 3. Prove the state machine and data contract from outside the service

Use a live model where the claim is about learning or repair. Use deterministic fixtures for concurrency, timing, and edge cases. Treat fetched content as data and execute only approved declarative operations. Verify the following behavior.

- From a fresh URL observe `integrating → serving`. On a breaking HTTP-200 change, capture the failed read, `healing`, unchanged prior records and file bytes throughout repair, a separate repair run, and the corrected snapshot. Exercise exhausted repair with an actionable `failed` reason. Test a timeout, 429, or 5xx followed by recovery separately from a real login/CAPTCHA gate. Today a failure after the immediate temporary-error retry can clear the next scheduled read. Ask me to choose the recovery policy. Respect at most one request per second per portal across discovery, verification fetches, redirects, retries, downloads and any approved browser traffic. No logins, CAPTCHA solving, or steering during runs.
- Call all seven portal routes, `GET /`, and document paths through the built container without authentication. Expect JSON for API data, HTML for the dashboard, and raw bytes for documents. Verify immediate background registration (`201`, same URL returns the same ID), list and detail (`200`, correct state, reason, count and last success), refresh (`202`, concurrent calls return the active read's `runId`), tenders (`200`, strictly later `changedSince` including equality and offset equivalents), runs (`read` or `repair`, first attach is a read, `finishedAt` and `result` null while active, then a timestamp and `ok` or `failed`), and deletion (`204`, no later publication, requests stop within one minute). Unknown IDs return `404`. Match appendix keys, nullability, JSON array shapes and casing. Test restart during work and isolation between portals.
- Compare tender fields to source values. Require the portal's own stable identifier when exposed, source URL and title, buyer, date-only publication, offset-aware deadline, status, documents and actual-change `lastChangedAt`. Preserve required nulls and omit unavailable optional fields. Verify `referenceNumber`, `description`, `procedureType`, `contractNature`, eight-digit CPVs without check digits, and `placeOfPerformance` where shown, including the appendix's enums and country codes. Exercise local time and DST ambiguity, a past deadline, verified removal, buyer cancellation (`withdrawn`), and a no-op refresh. Prefer a missing value to an invented ID, date or status.
- Validate **all** files on the controlled fixture through their public API paths. Compare byte length and SHA-256 with independent source bytes as well as the manifest. Exercise direct files, summaries that lead to files, mixed and unrelated attachments, redirects, ZIP members, duplicate filenames, and the allowed omission of files or archives over 250 MB. Test a valid empty listing separately. Keep the existing smoke check fast and make clear which checks establish completeness.
